# Data Flow — MVP 1

## Пропонована модель даних
| Сутність | Мінімальні дані |
|---|---|
| Клієнт | ID, ідентифікатор каналу, ім’я, телефон |
| Згода | Клієнт, тип повідомлень, стан, час і спосіб отримання/відкликання |
| Послуга | ID, назва, ціна, тривалість, активність |
| Майстер | ID, ім’я, послуги/спеціалізації, посилання на графік |
| Заявка | ID, клієнт, обрані дані, відсутні дані, стан, причина передачі |
| Запис | ID, заявка, майстер, послуга, початок/кінець, статус, зовнішній ID, версія |
| Фонове завдання | ID, тип, запис і версія, час виконання, стан, кількість спроб |
| Подія | ID операції, тип, час, виконавець, результат |

Ці сутності є логічною моделлю, не готовою схемою БД. Час зберігати однозначно з часовим поясом салону для показу; конкретний пояс ще невідомий.

## Новий запис
1. Клієнт → бот: послуга/запит. AI за потреби консультує за базою знань.
2. Бот/n8n → backend: структурована заявка й ідентифікатор клієнта.
3. Backend → довідники та календар: перевірка послуги, майстра, тривалості й слотів.
4. Клієнт обирає слот, надає ім’я та телефон і підтверджує підсумок.
5. Backend перевіряє право доступу, дані та повтор операції; виконує захищене від конфліктів резервування.
6. Після достовірного успіху зберігає запис і подію для повідомлень. У разі невідомого результату запускає звірку, не повідомляє про успіх.
7. n8n надсилає підтвердження клієнту та інформацію адміністратору; створює нагадування за погодженими правилами.

## Перенесення та скасування
Перевірити власника запису й бізнес-правила → перевірити актуальний стан → змінити резервування через backend → зберегти нову версію → скасувати застарілі фонові дії → повідомити сторони.
Якщо зміна в CRM не завершена, позначити потребу звірки. Не втрачати попередній слот при невдалій спробі перенесення.

## Нагадування
Планувальник → актуальна версія запису → перевірка статусу, часу й згоди → відправлення → фіксація результату. Повторна доставка використовує сталий ключ повідомлення; вже скасований запис не має породжувати нагадування.

## Складна заявка й адміністративні дії
AI або сценарій → заявка з причиною передачі → сповіщення адміністратора → рішення через backend → оновлення стану → відповідь клієнту. Команди адміністратора перевіряють роль і фіксують автора зміни.

## Стани — пропозиція
Заявка: чернетка → очікує підтвердження → обробляється → завершена; відгалуження: передана адміністратору, відхилена.
Запис: очікує резервування → підтверджений → завершений / скасований / неявка. Окремий статус синхронізації: узгоджено / потребує звірки / помилка.
Завдання: очікує → у роботі → виконано / помилка. Повторні спроби обмежені; остаточний збій видимий адміністратору.

## Межі даних
AI отримує лише необхідний контекст. Налаштування й база знань — довірені дані салону; повідомлення клієнта — недовірений ввід. Строки зберігання контактів, діалогів і журналів та процедура видалення потребують погодження.
