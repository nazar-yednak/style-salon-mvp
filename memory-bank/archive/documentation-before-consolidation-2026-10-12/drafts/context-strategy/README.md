# Context Strategy — Salon Agent, MVP 1
Погоджено користувачем 2026-10-12. Стратегія для реалізації й тестування; код ще не створено. Пов’язана [Model Strategy](../../model-strategy.md).

## 1. Бюджет контексту
Ліміти сценаріїв погоджені раніше; розподіл на операції погоджений як початкова політика для тестів.

| Рівень | Input | Видимий output | Reasoning | Усі AI-спроби |
|---|---:|---:|---:|---:|
| Типовий сценарій, сумарно | 6000 | 1000 | 0 | 5 |
| Складний сценарій, сумарно | 24000 | 3000 | 2000 | 12 |
| Коротка операція: намір, поля, передача | До 1000 | До 200 | 0 | У межах сценарію |
| Типова консультація | До 3000 | До 500 | 0 | У межах сценарію |
| Складна консультація або підбір | До 5000 | До 800 | До 1000 за умовою | У межах сценарію |
| Підсумок адміністратору | До 5000 | До 500 | 0 | У межах сценарію |

Залишок сценарію, грошовий бюджет і резерв для завершення мають пріоритет над максимумом операції. Кілька максимальних викликів можуть не поміститися в сценарій.
Перед спробою backend підраховує або консервативно оцінює весь запит, включно зі схемами tools; перевіряє токени, кошти й спроби; скорочує необов’язкове; резервує бюджет. Після відповіді звіряє usage.
На 80% ліміту скорочуємо контекст і переходимо до стандартного сценарію. Типовий сценарій один раз переходить у складний без скидання лічильників.

## 2. Архітектура промпту
| Блок | Зміст | Правило |
|---|---|---|
| Системні правила | Роль, українська, повноваження, захист даних | Короткі, стабільні, версійовані |
| Правила операції | Завдання, результати, уточнення й передача | Лише поточна операція |
| Схема результату / tools | JSON Schema й необхідні інструменти | Без зайвих схем |
| Структурований стан | Намір, поля, відсутні дані, ID й версія | Джерело — backend |
| Матеріали салону | Відібрані затверджені фрагменти | Джерело, версія, актуальність |
| Пам’ять діалогу | Підсумок і потрібні останні репліки | У межах бюджету |
| Поточний запит / tool results | Повідомлення й актуальні результати | Дані, не інструкції |

Повідомлення клієнта й документи не змінюють системні правила. Модель не вигадує поля, ціни чи доступність. Підтвердження запису походить від backend після резервування. Без джерела — уточнення або адміністратор.
Memory Bank, кошториси, технічні логи й повна Model Matrix не входять у клієнтський промпт.

## 3. Conversation Memory
- Стан сценарію: структуровані поля, намір, етап, версія та бюджет.
- Останні репліки: початково до 6 релевантних повідомлень; токенний бюджет важливіший за кількість.
- Підсумок: потреби, підтверджені факти, невизначеності й питання замість старої частини розмови.
- Постійні дані: клієнт, згоди, записи й історія операцій — вибірково за ID та правами.
- База знань: затверджені матеріали за темою.

Історія та стан заявки — різні сутності. Підсумок не перезаписує підтверджені поля БД. Клієнтська пам’ять ізольована; новий сценарій отримує лише доречні дані.
Строки зберігання, підсумків і видалення ще потрібно визначити.

## 4. Indexing Strategy
MVP без embeddings і векторної бази.
Метадані матеріалів: document_id, section_id, topic, service_id, master_id, language, version, status, updated_at, source, text.
Порядок: точні ID/фільтри → категорії, теги й синоніми → текстовий пошук → кілька релевантних фрагментів у бюджеті → уточнення/людина при відсутності джерела.
Розбиття за завершеними темами: послуга, підготовка, правило скасування. Виняток не відривати від правила.
Ціни, тривалість і слоти — зі структурованого джерела. Чернетки й неактивні версії виключені.
Перегляд embeddings: регулярні пропуски пошуку, які не усуваються простими засобами, або суттєве зростання матеріалів.

## 5. Правила стискання
Тригер: запит не вкладається в бюджет операції або прогнозується перевищення сценарію.
1. Прибрати дублікати й замінені tool results.
2. Прибрати нерелевантні джерела й старі версії.
3. Залишити потрібні останні репліки.
4. Стару частину замінити підсумком.
5. Якщо недостатньо — уточнення або людина.

Зберігати підтверджені поля, ID, заперечення, обмеження клієнта, невизначеності, стан резервування, відкриті питання й причину передачі.
Ціни, час, згоду й критичні правила не переказувати модельним стисканням: подавати структуровано або дослівно.
Підсумок розділяє факти, припущення й питання. Створюється після значущого накопичення; його виклик входить у бюджет.

## 6. Caching Strategy
| Об’єкт | Ключ / механізм | Анулювання |
|---|---|---|
| Правила й схеми | Стабільна версія; provider prompt caching за підтримки | Зміна промпту/схеми |
| Матеріали | ID, версія, мова, тема | Оновлення, деактивація, видалення |
| Пошук | Нормалізований запит, фільтри, версія бази | Зміна матеріалів |
| Каталог | Короткостроково з версією | Зміна послуг, цін, майстрів |
| Підсумок | Клієнт, сценарій, межа охоплених реплік | Суттєві уточнення |

Кеш не підтверджує слот чи бронювання: перед зміною перевірити актуальність. Персональні відповіді не кешувати спільно. FAQ — затверджений текст замість довільної генерації.
TTL визначити після вибору CRM. Економію provider caching враховувати лише за підтвердженої підтримки й usage.

## 7. API Parameter Policy
| Параметр / контроль | Політика |
|---|---|
| model | Явний ID матриці; лог фактичної моделі |
| response_format | JSON Schema для наміру, полів, рекомендацій, передачі |
| Підтримка | Endpoint підтримує всі обов’язкові параметри |
| tools | Мінімальні потрібні інструменти й схеми |
| tool_choice | Обмеження сценарієм; без необмежених дій |
| max_tokens / max_completion_tokens | За сумісністю endpoint; спільний бюджет reasoning і видимого output |
| Reasoning | Вимкнений для простих; умовний для складних; S/G — effort |
| temperature | Низька для класифікації/полів за підтримки; значення за тестами |
| Streaming | Можливий для консультації; бізнес-дія після повної валідації |
| Timeout | Окремий від CRM; значення за latency-тестами |
| Usage | Кожна спроба; невідоме не означає нуль |

Не надсилати непідтримувані параметри. JSON не доводить істинність. Профілі основних і резервних моделей перевірити перед запуском.

## 8. Retry Strategy
1 retry/операцію, 2/сценарій; 1 fallback/операцію, 2/сценарій; максимум 3 спроби/операцію. Усі входять у ліміти 5/12 та бюджет.
| Ситуація | Дія |
|---|---|
| Rate limit, тимчасовий збій | Retry із затримкою, Retry-After за наявності |
| Тайм-аут AI | Перевірити доступний статус/usage; врахувати можливу оплату |
| Невалідна схема | Одна спроба виправлення з короткою помилкою |
| Контекст завеликий | Скоротити, не повторювати незмінений запит |
| Немає даних/джерел | Уточнення або людина |
| Модель недоступна | Погоджений fallback у бюджеті |
| Підозрілі факти/заборонена дія | Відхилити; сильніша модель не замінює перевірку |
| Вичерпані ліміти | Код, шаблон, адміністратор |
| Тайм-аут CRM | Звірити запис до повтору бізнес-дії |

Кожна спроба повторно перевіряє бюджет. Backend, n8n і SDK використовують спільний лічильник; вкладені повтори не множать виклики.

## Питання до реалізації
Початкові питання уточнено погодженими рішеннями нижче. Точні API-профілі й механізм українського пошуку залишаються задачами тестування. Перевірити втрату заперечень при стисканні, ізоляцію клієнтів, інвалідацію кешу й спільні retry counters.

## Context Architecture v1 — погоджені уточнення
Погоджено користувачем 2026-10-12. Цей розділ уточнює попередні загальні правила; реалізацію не виконано.

### Матеріали й промпти
Після отримання Google Drive-файлів перевірити затверджені матеріали, розділити за завершеними темами й виміряти токени. Передавати фрагменти в межах бюджету. Бюджети 1000/3000/5000 input — стартові межі, які уточнюються після тестів.
Окремий версійований шаблон і JSON-схема для кожної операції в коді. Спільні правила: українська, джерела для фактів, уточнення неоднозначностей, без самостійного підтвердження запису.

### Пам’ять і завершення сценарію
Повідомлення, summary й стан діалогу — у технічній PostgreSQL. Бізнес-дані й остаточний реєстр записів — Google Sheets. Модель отримує потрібні поля через backend.
Сценарій завершується після виконання дії або передачі адміністратору; після 30 хв неактивності закривається діалоговий сценарій. Незавершена заявка зберігається окремо. Повернення клієнта починає новий сценарій з потрібним станом.
Закриття діалогу не скасовує заявку/запис. Утримання слоту має незалежний строк 30 хв.
Строк персональних даних — 2 календарні місяці після завершення сценарію/візиту з винятком активних майбутніх записів. Адміністратор відповідає за матеріали.

### Summary
Створювати, коли історія перевищує 1000 токенів або повний запит не вкладається в бюджет; враховувати бюджет самого виклику. Не повторювати без нових суттєвих даних.
Максимум 300 токенів: потреба, підтверджені побажання, заперечення, невизначеності, питання, межа охопленої історії. Точні поля заявки залишаються структурованими поза summary.

### Пошук і кеші
Тематичні фрагменти індексу — у PostgreSQL; категорії, теги, нормалізація й керований словник синонімів. Конкретний текстовий механізм обрати за українськими тестами. Embeddings не використовуються.
Кнопка адміністратора «Оновити базу знань»: завантажити, перевірити, активувати нову версію; при помилці залишити попередню.
Версія каталогу/бази входить у ключ кешу; зміна збільшує версію. Старі записи не використовуються. TTL: каталог/FAQ до 5 хв, пошук до 1 хв, слоти для показу до 15 с; перед утриманням свіжа перевірка.
Provider caching увімкнути після перевірки endpoint/usage; економію не включати до базового кошторису.

### API й повтори
Намір/поля: reasoning вимкнений, JSON Schema, мінімальний output. Консультації: відібрані джерела; складний підбір — умовне reasoning. Temperature/effort уточнити тестами підтримуваних параметрів.
Окрема спроба: коротка AI до 20 с, складна до 45 с, Google API до 15 с. Загальний deadline AI-операції: 30 с коротка, 60 с складна, включно з очікуванням/retry/fallback. Спроба отримує лише залишок часу.
429: Retry-After за наявності; без нього одна дозволена повторна спроба через 2–4 с із випадковим розкидом. За відсутності часу/бюджету — резервний сценарій. Попередні ліміти спроб зберігаються.
Резерв завершення — 20% бюджету сценарію.

### Відновлення після простою
На запуску звірити незавершені операції, звільнити прострочені утримання, перевірити Sheets/Calendar. Бізнес-дії не повторювати до звірки.
Пропущені нагадування: до початку візиту одне актуальне повідомлення замість кількох прострочених; після початку пропустити. Сталий ключ повідомлення захищає від дублювання.

### Приймання
50 українських тестових діалогів: консультації, поля, неоднозначні дати, зміна побажань, передача, довга історія, збої, повтори.
Усі критичні бізнес-тести проходять; немає чужих даних, подвійних бронювань чи хибного підтвердження. Щонайменше 95% правильних результатів для наміру/полів на погодженому наборі; усі тестові заперечення збережено в summary. Консультації оцінює адміністратор.
Ці критерії — цілі, не результати виконаних тестів. Окремо погодити розподіл тестів та точний протокол оцінки правильності.
