# Дані й потоки — Стиль салон, MVP 1

## Власники даних
| Сутність | Мінімальні поля | Сховище |
|---|---|---|
| Клієнт / згода | ID, Telegram user.id, ім’я, телефон; стан/час згоди | Sheets |
| Послуга / майстер | ID, назва, ціна, тривалість, активність, спеціалізація | Sheets |
| Графік | Робочий час, обід, буфер, виключення | Бізнес-налаштування Sheets; Calendar відображення |
| Заявка | ID, клієнт, обрані поля, відсутнє, причина передачі | Sheets |
| Запис / утримання | ID, майстер, час початку/кінця, стан, expires_at, версія, зовнішній ID | Sheets; технічний захист PostgreSQL |
| Розмова / summary | Client/scenario ID, репліки, підсумок, охоплена історія | PostgreSQL |
| Завдання / подія / usage | ID, тип, час, спроби, версія запису, результат, токени/вартість | Технічний PostgreSQL/n8n |
| Фрагмент знань | ID, тема, версія, джерело, статус, текст | Drive джерело → індекс PostgreSQL |

Це логічна модель, не реалізована схема БД. Час показувати Europe/Kyiv; зберігати однозначні timestamps. Згода, ID, ціни й час не відновлюються з summary.

## Запис
1. Telegram → backend: ідентифікація й намір; AI лише за потреби.
2. Каталог/знання → вибір послуги й майстра → доступні варіанти.
3. Клієнт підтверджує підсумок заявки. Backend перевіряє дані/повтор і під блокуванням створює 30-хвилинне утримання у робочий час.
4. Sheets оновлюється, Calendar відображає утримання; невідомий результат позначається для звірки.
5. Адмін отримує заявку; через 15 хв — нагадування, якщо ще не вирішено.
6. Адмін підтверджує/відхиляє/пропонує час. Прострочений hold не можна підтвердити без повторної перевірки.
7. Лише після достовірного успіху → повідомлення клієнту й задачі нагадувань.
Поза робочим часом — заявка без гарантованого утримання.

## Зміни та повідомлення
Перенесення: перевірка власника/правил → нова доступність → рішення адміна → успішна зміна → нова версія; старий запис зберігати до успіху. Скасування звільняє слот.
Нагадування: актуальна версія + статус + згода → відправлення зі сталим ключем. Правила 24 год/2 год та відновлення: [бізнес-правила](business-rules.md), [контекст](context-strategy.md).
Адмін фіксує завершення й неявку; статистика розраховується кодом.

## AI-виклик
Код чи AI → бюджети й резерв → вибір моделі → мінімальний контекст → API → формат/зміст/ID → usage і звірка → дозволений retry/fallback або людина.
Пам’ять одного клієнта не змішується з іншими. Закриття діалогу через 30 хв неактивності не скасовує заявку/запис.

## Стани
Робоча модель для реалізації: заявка — чернетка/очікує адміна/передана/завершена/відхилена; утримання — активне/прострочене/перетворене/звільнене; запис — підтверджений/скасований/завершений/неявка. Синхронізація окремо — узгоджено/потребує звірки/помилка.
Точні переходи/API-контракти потрібно перевірити тестами.
